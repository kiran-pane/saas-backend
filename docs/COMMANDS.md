# Command Reference

Every command you need to set up, run, migrate, and operate this project —
locally and via Docker. Organized so you can jump straight to the section
you need.

---

## 1. First-time setup

```bash
# clone / cd into the project
cd saas-backend

# copy env template and fill in real values
cp .env.example .env
#   required at minimum: APP_SECRET_KEY, DB_PASSWORD
#   required for LLM features: OPENAI_API_KEY and/or ANTHROPIC_API_KEY
#   required for Google sign-in: GOOGLE_CLIENT_ID

# generate a real secret key instead of the placeholder
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
# paste the output into APP_SECRET_KEY in .env
```

### Local (non-Docker) dependency install

```bash
pip install poetry                     # if you don't have it
poetry install                         # installs from pyproject.toml
poetry shell                           # activate the virtualenv (optional)
```

## 2. Docker Compose — full stack

All commands below assume you're in the project root (where `docker-compose.yml` lives).

### Build & start everything

```bash
# build images (only needed after Dockerfile/dependency changes)
docker compose build

# start infra first, then run migrations, then bring up the app
docker compose up -d postgres redis pgbouncer
docker compose up -d                    # starts api, workers, beat, flower too

# the api container's entrypoint runs `alembic upgrade head` automatically
# on every start — no separate manual migration step needed for the
# common case. See section 3 if you need to run migrations manually.
```

### Day-to-day

```bash
docker compose up -d                    # start everything (detached)
docker compose down                     # stop + remove containers (keeps volumes/data)
docker compose down -v                  # stop + remove containers AND volumes (wipes DB/Redis data)
docker compose restart api              # restart just the api service
docker compose ps                       # see what's running and its health status
```

### Logs

```bash
docker compose logs -f api              # tail api logs
docker compose logs -f worker-default   # tail default-queue worker logs
docker compose logs -f worker-llm-heavy # tail LLM ingestion worker logs
docker compose logs -f beat             # tail Celery Beat scheduler logs
docker compose logs -f postgres         # tail Postgres logs
docker compose logs --tail=200 -f       # tail last 200 lines from ALL services
```

### Rebuilding after code changes

```bash
# rebuild + recreate just the api service (fast iteration)
docker compose up -d --build api

# rebuild + recreate api and all worker services
docker compose up -d --build api worker-default worker-llm-heavy beat

# force a clean rebuild ignoring the Docker layer cache
docker compose build --no-cache api
```

### Scaling workers

```bash
# run 3 replicas of the default worker (audit/notifications/llm queues)
docker compose up -d --scale worker-default=3

# run 2 replicas of the heavy LLM ingestion worker
docker compose up -d --scale worker-llm-heavy=2
```

### Shelling into a running container

```bash
docker compose exec api bash            # shell into the api container
docker compose exec postgres psql -U saas_app -d saas_backend   # psql prompt
docker compose exec redis redis-cli     # redis-cli prompt
```

### One-off commands without starting the full stack

```bash
# run a throwaway container to execute a single command, then remove it
docker compose run --rm api alembic upgrade head
docker compose run --rm api python -m pytest
docker compose run --rm api python -c "from app.config import settings; print(settings.ENV)"
```

## 3. Alembic (database migrations)

Run these either inside a container (`docker compose exec api <cmd>` /
`docker compose run --rm api <cmd>`) or locally if you have `DATABASE_URL`
pointed at a reachable Postgres.

```bash
# apply all pending migrations (safe to run repeatedly — no-ops if already current)
alembic upgrade head

# apply migrations up to a specific revision
alembic upgrade 0001_initial_schema

# roll back the most recent migration
alembic downgrade -1

# roll back to a specific revision (or "base" to undo everything)
alembic downgrade 0001_initial_schema
alembic downgrade base

# see the current revision applied to the DB
alembic current

# see full migration history
alembic history --verbose

# create a new empty migration to hand-edit
alembic revision -m "add invoices table"

# create a new migration with autogenerated diff from your SQLAlchemy models
# (review the output carefully — autogenerate misses RLS policies,
# partitioning, and CHECK constraints; those need to be added by hand,
# same as 0001_initial_schema.py and 0002_google_oauth.py already do)
alembic revision --autogenerate -m "add invoices table"
```

**Via Docker:**

```bash
docker compose exec api alembic upgrade head
docker compose exec api alembic downgrade -1
docker compose exec api alembic revision -m "add invoices table"
docker compose exec api alembic current
```

## 4. Data seeding

Two independent, both idempotent (safe to run repeatedly, in any environment):

```bash
# 1. Sync the permission catalog (app/core/security/permission_catalog.py)
#    into the DB. The baseline set is already inserted by the 0001
#    migration — run this again any time you ADD a new permission to the
#    catalog in code, instead of writing a new migration for reference
#    data. Upserts by `code`; never touches existing role grants.
docker compose exec api python -m app.seeds.run permissions

# 2. Optionally bootstrap a demo tenant + Owner user, controlled by
#    SEED_TENANT_SLUG / SEED_TENANT_NAME / SEED_ADMIN_EMAIL /
#    SEED_ADMIN_PASSWORD in .env. No-op (and doesn't error) if
#    SEED_TENANT_SLUG is unset — this never runs by accident.
docker compose exec api python -m app.seeds.run dev-data

# or run both in one shot
docker compose exec api python -m app.seeds.run all
```

Local (non-Docker) equivalents:

```bash
python -m app.seeds.run permissions
python -m app.seeds.run dev-data
python -m app.seeds.run all
```

**Auto-run on container start:** set `SEED_PERMISSIONS_ON_STARTUP=true` in
`.env` to have `docker/entrypoint.sh` run the permission sync automatically
after every `alembic upgrade head` — safe to leave on since it's a pure
upsert. `dev-data` is never auto-run on startup (by design — you don't
want a demo tenant silently appearing in a shared environment), always
trigger it explicitly with the command above.

**Why "Owner" needs this:** every tenant gets "Owner" and "Member" roles
seeded automatically at creation (`rbac_service.seed_default_roles`), but
"Owner" only actually has permissions attached if the `permissions` table
already has rows in it — which is why the migration seeds the baseline
catalog directly, and why you should run the sync command above before
creating tenants in a fresh environment that skipped the bundled
migration for any reason (e.g. a hand-rolled schema).

## 5. Uvicorn (running the API directly)

Use these for local development without Docker. In Docker, the
`docker-compose.yml` command block already runs the right one.

```bash
# development — auto-reload on file changes, single process
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

# development with more verbose logging
uvicorn app.main:app --reload --log-level debug

# production-style — multiple worker processes, no reload
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4

# production behind a process manager, binding to a Unix socket instead of a port
uvicorn app.main:app --uds /tmp/uvicorn.sock --workers 4
```

**Alternative for production: Gunicorn managing Uvicorn workers**
(gives you Gunicorn's process management — auto-restart on crash, graceful
reload — while still using Uvicorn's ASGI worker class):

```bash
pip install gunicorn
gunicorn app.main:app \
  --worker-class uvicorn.workers.UvicornWorker \
  --workers 4 \
  --bind 0.0.0.0:8000 \
  --timeout 60 \
  --graceful-timeout 30 \
  --access-logfile - \
  --error-logfile -
```

## 6. Celery (background workers, beat, monitoring)

### Running workers locally (non-Docker)

```bash
# default queue group: audit, notifications, quick llm tasks
celery -A app.worker_main.celery_app worker -Q audit,notifications,llm --concurrency=10 --loglevel=info

# heavy queue: document ingestion / embedding (kept separate so it never
# starves quick audit/notification tasks — see blueprint section 6)
celery -A app.worker_main.celery_app worker -Q llm_heavy --concurrency=4 --loglevel=info

# scheduler (partition creation, token cleanup — see celery_app.conf.beat_schedule)
celery -A app.worker_main.celery_app beat --loglevel=info

# a single worker listening to every queue (fine for local dev, NOT for prod)
celery -A app.worker_main.celery_app worker -Q audit,notifications,llm,llm_heavy --concurrency=4
```

### Monitoring / inspecting workers

```bash
# Flower web UI (also runs automatically via docker-compose, at :5555)
celery -A app.worker_main.celery_app flower --port=5555 --basic_auth=admin:change-me

# list currently active tasks across workers
celery -A app.worker_main.celery_app inspect active

# list registered task names
celery -A app.worker_main.celery_app inspect registered

# check worker liveness ("pong" from every connected worker)
celery -A app.worker_main.celery_app inspect ping

# see queue lengths (requires redis-cli, since broker is Redis)
docker compose exec redis redis-cli -n 1 llen audit
docker compose exec redis redis-cli -n 1 llen llm_heavy
```

### Queue management

```bash
# purge ALL pending tasks from every queue — destructive, dev/debug only
celery -A app.worker_main.celery_app purge -f

# purge a specific queue
celery -A app.worker_main.celery_app amqp queue.purge llm_heavy   # (Redis broker: use redis-cli DEL instead)
docker compose exec redis redis-cli -n 1 del llm_heavy
```

### Via Docker (workers already run automatically; use these to inspect/debug)

```bash
docker compose exec worker-default celery -A app.worker_main.celery_app inspect active
docker compose exec worker-default celery -A app.worker_main.celery_app inspect ping
docker compose logs -f worker-llm-heavy
```

### Manually triggering a task (for testing)

```bash
docker compose exec api python -c "
from app.tasks.audit_tasks import write_audit_log
write_audit_log.delay(
    tenant_id='00000000-0000-0000-0000-000000000000',
    actor_id=None, action='test.manual_trigger',
    resource_type=None, resource_id=None, metadata={},
)
print('enqueued')
"
```

## 8. Database access & maintenance

```bash
# psql shell directly against Postgres (bypassing PgBouncer — fine for admin work)
docker compose exec postgres psql -U saas_app -d saas_backend

# psql through PgBouncer (what the app actually uses)
docker compose exec pgbouncer psql -h localhost -p 6432 -U saas_app -d saas_backend

# dump the database (backup)
docker compose exec postgres pg_dump -U saas_app -d saas_backend -F c -f /tmp/backup.dump
docker compose cp postgres:/tmp/backup.dump ./backup.dump

# restore from a dump
docker compose cp ./backup.dump postgres:/tmp/backup.dump
docker compose exec postgres pg_restore -U saas_app -d saas_backend --clean /tmp/backup.dump

# check RLS is actually enabled on a table (sanity check after migrations)
docker compose exec postgres psql -U saas_app -d saas_backend \
  -c "SELECT relname, relrowsecurity FROM pg_class WHERE relname = 'users';"

# check audit_logs partitions that exist
docker compose exec postgres psql -U saas_app -d saas_backend \
  -c "SELECT inhrelid::regclass FROM pg_inherits WHERE inhparent = 'audit_logs'::regclass;"
```

## 10. Creating your first tenant, user, and role (end-to-end smoke test)

```bash
BASE=http://localhost:8000/api/v1

# 1. create a tenant WITH a bootstrap Owner user in one call — owner_email
#    + owner_password create the user and assign the Owner role (which
#    has every seeded permission, see section 4) atomically.
curl -s -X POST $BASE/platform/tenants \
  -H "Content-Type: application/json" \
  -d '{"slug": "acme", "name": "Acme Inc", "owner_email": "owner@acme.com", "owner_password": "correct-horse-battery-staple"}' \
  | tee /tmp/tenant.json

# (alternative for a quick throwaway demo tenant instead of a one-off curl:
#  set SEED_TENANT_SLUG/SEED_TENANT_NAME/SEED_ADMIN_EMAIL/SEED_ADMIN_PASSWORD
#  in .env, then: docker compose exec api python -m app.seeds.run dev-data)

# 2. log in as that owner
curl -s -X POST $BASE/auth/login \
  -H "X-Tenant-Slug: acme" -H "Content-Type: application/json" \
  -d '{"email": "owner@acme.com", "password": "correct-horse-battery-staple"}' \
  | tee /tmp/tokens.json

# 3. call an authenticated route
ACCESS=$(python3 -c "import json;print(json.load(open('/tmp/tokens.json'))['access_token'])")
curl -s $BASE/users/me -H "X-Tenant-Slug: acme" -H "Authorization: Bearer $ACCESS"

# 4. confirm the owner can actually manage RBAC (proves permissions were seeded correctly)
curl -s $BASE/admin/roles -H "X-Tenant-Slug: acme" -H "Authorization: Bearer $ACCESS"
```

## 12. Quick troubleshooting

```bash
# api won't start — check migration/entrypoint logs first
docker compose logs api | head -50

# "no tenant in context" errors — you forgot the X-Tenant-Slug header
curl ... -H "X-Tenant-Slug: acme" ...

# confirm which containers are unhealthy
docker compose ps
docker inspect --format='{{json .State.Health}}' $(docker compose ps -q postgres) | python3 -m json.tool

# nuke everything and start completely fresh (destroys all data)
docker compose down -v
docker compose build --no-cache
docker compose up -d
```
